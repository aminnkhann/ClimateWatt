# از سه اسکریپت تا یک پایپ‌لاین داده

## چرا این پروژه ساخته شد؟

پروژه با یک سؤال ساده شروع شد: اگر مشاهدات ساعتی آب‌وهوا را با قیمت برق آلمان
روی یک خط زمانی UTC قرار دهیم، چه چیزی به دست می‌آوریم؟

پاسخ در یک مرحله ساخته نشد. تیم ابتدا با چند اسکریپت و فایل CSV شروع کرد، سپس
تست، CI، ماژول‌های قابل استفادهٔ مجدد، PostgreSQL و Docker را به پروژه اضافه کرد.

مهم‌ترین درس این است که پایپ‌لاین داده فقط کد تبدیل DataFrame نیست. قراردادهای
مشترک برای timestampها، نام ستون‌ها، کلیدهای کسب‌وکار، تنظیمات، تراکنش‌ها، تست‌ها
و دستورهای اجرا نیز بخشی از محصول هستند.

## نقشهٔ راه

پروژه در سه سطح طراحی شده است:

1. **Level 1 — مقدماتی:** اسکریپت‌های قابل اجرا و فایل‌های CSV.
2. **Level 2 — متوسط:** کد قابل استفادهٔ مجدد، PostgreSQL، تست و Docker.
3. **Level 3 — نیمه‌حرفه‌ای:** زمان‌بندی، retry، لاگ و اجرای روزانه با Airflow.

معماری موردنظر:

```text
Open-Meteo API       فایل/API قیمت برق
      |                       |
      +---- کلاینت‌های Python قابل استفادهٔ مجدد ----+
                                      |
                              جداول خام PostgreSQL
                                      |
                              تبدیل با pandas
                                      |
                         analytics.weather_energy_hourly
                                      |
                             orchestration با Airflow
```

UTC زبان مشترک دو منبع است. نمونهٔ فعلی از دادهٔ آب‌وهوای هامبورگ و ناحیهٔ بازار
برق `DE-LU` استفاده می‌کند.

## اکنون چه چیزهایی ساخته شده است؟

### کلاینت‌های منبع

```text
src/weather_energy/clients/
├── weather_client.py
└── price_client.py
```

weather client دادهٔ Open-Meteo را دریافت و اعتبارسنجی می‌کند. price client دادهٔ
قیمت را می‌خواند، نرمال می‌کند، اعتبارسنجی می‌کند و به سطح ساعتی می‌رساند. هر دو
کلاینت DataFrame برمی‌گردانند.

### Transformation

فایل `src/weather_energy/transform/weather_energy.py` timestampها را UTC می‌کند،
مقادیر لازم را اعتبارسنجی می‌کند، دو منبع را Join می‌کند و کلید تحلیلی زیر را
بررسی می‌کند:

```text
timestamp_utc + city + market_area
```

بنابراین چند شهر و چند ناحیهٔ بازار قابل پشتیبانی هستند و کلید تحلیلی تکراری ایجاد
نمی‌شود.

### مدل پایگاه داده

فایل `sql/create_tables.sql` جداول زیر را می‌سازد:

```text
raw.weather_hourly
raw.electricity_price_hourly
analytics.weather_energy_hourly
```

جداول raw رکوردهای منبع را نگه می‌دارند و جدول analytics رکوردهای Join‌شده را ذخیره
می‌کند. کلیدهای اصلی PostgreSQL از تکرار رکوردهای کسب‌وکار جلوگیری می‌کنند.

### Loading و orchestration

ترتیب اجرای Level 2:

```text
دریافت آب‌وهوا
  → خواندن و آماده‌سازی قیمت
  → اعتبارسنجی و Join
  → آماده‌سازی پایگاه داده
  → بارگذاری آب‌وهوای خام
  → بارگذاری قیمت خام
  → بارگذاری دادهٔ تحلیلی
```

loaderها از upsertهای conflict-aware استفاده می‌کنند. مالک تراکنش runner است تا
تمام نوشتن‌های یک اجرای پایپ‌لاین بتوانند در یک تراکنش مدیریت شوند.

## هنگام اجرای پروژه چه انتظاری داریم؟

### Level 1

از ریشهٔ repository اجرا کنید:

```bash
python scripts/get_weather.py
python scripts/prepare_prices.py
python scripts/build_dataset.py
```

دستور اول دادهٔ ساعتی آب‌وهوا را دانلود می‌کند، دستور دوم قیمت را به دادهٔ ساعتی
UTC تبدیل می‌کند و دستور سوم فایل نهایی Join‌شده را می‌سازد.

### Level 2

وابستگی‌های پایگاه داده را نصب و PostgreSQL را اجرا کنید:

```bash
pip install -e ".[database,dev]"
docker compose up -d postgres
python -m weather_energy.run_pipeline
```

runner بازهٔ آب‌وهوای تنظیم‌شده را دریافت می‌کند، قیمت‌ها را آماده می‌کند، جداول را
در صورت نیاز می‌سازد و رکوردهای raw و analytics را upsert می‌کند. اجرای دوباره با
کلیدهای یکسان نباید رکورد تکراری ایجاد کند.

برای بررسی پایگاه داده:

```sql
SELECT COUNT(*) FROM raw.weather_hourly;
SELECT COUNT(*) FROM raw.electricity_price_hourly;
SELECT COUNT(*) FROM analytics.weather_energy_hourly;

SELECT timestamp_utc, city, market_area
FROM analytics.weather_energy_hourly
ORDER BY timestamp_utc DESC
LIMIT 10;
```

پروژه هنوز یک batch pipeline دستی است؛ هنوز Airflow، streaming، dashboard یا
deployment production نیست.

## درس‌هایی برای پروژه‌های بعدی

### قراردادها را قبل از توسعهٔ موازی مشخص کنید

بیشترین مشکل‌های integration از تفاوت‌های کوچک در signature توابع، نوع timestamp،
ستون‌های جدول و مالکیت تراکنش ایجاد شدند. این قراردادها باید قبل از جدا شدن branchها
مشخص شوند.

### timezone بخشی از مدل داده است

UTC فقط قالب نمایش نیست. تعیین می‌کند که دو منبع درست Join شوند و تغییر ساعت تابستانی
باعث ساعت گمشده یا تکراری نشود.

### کلیدها را هم در کد و هم در دیتابیس enforce کنید

اعتبارسنجی DataFrame خطا را زود پیدا می‌کند. کلید اصلی دیتابیس و conflict handling
از اجرای مجدد و نوشتن همزمان محافظت می‌کنند. هر دو لایه لازم‌اند.

### اسکریپت‌ها را نازک و ماژول‌ها را reusable نگه دارید

اسکریپت برای کاربر راحت است، اما ماژول برای تست، runner و Airflow قابل استفاده است.
تکرار منطق در هر دو محل، تغییرات آینده را پرریسک می‌کند.

### رفتار خطا را تست کنید

تست‌های ارزشمند فقط دادهٔ تمیز را بررسی نمی‌کنند؛ پاسخ خراب API، timestamp نامعتبر،
ستون ناقص، DST، قیمت نامعتبر و کلید تکراری را هم مستند می‌کنند.

### Review بخشی از طراحی است

Reviewها signature قدیمی، تعارض schema، credential داخل کد، فرض اشتباه Join و مشکل
مصرف حافظه را پیدا کردند. بنابراین review فقط بررسی style نیست؛ ابزار بهبود معماری
است.

## مرحلهٔ بعد: orchestration با Airflow

Level 3 را زمانی شروع کنید که Level 2 از یک Docker volume خالی با موفقیت اجرا شده
باشد و دو اجرای پشت‌سرهم کلید تکراری نسازند.

نام DAG پیشنهادی:

```text
weather_energy_daily
```

DAG باید توابع تست‌شدهٔ `src/weather_energy/` را صدا بزند و نباید منطق API، پاک‌سازی،
تبدیل یا database را داخل خودش تکرار کند.

جریان پیشنهادی:

```text
fetch_weather  ──────> load_weather_raw ────┐
                                             ├──> build_analytics ──> validate_analytics
fetch_prices   ──────> load_prices_raw  ────┘
```

فعالیت‌های Level 3:

1. اضافه کردن سرویس‌های Airflow با Docker رسمی و نسخه‌گذاری‌شده.
2. mount کردن `dags/`، `src/` و `sql/` در containerها.
3. ساخت `dags/weather_energy_daily.py`.
4. تنظیم schedule روزانهٔ ساعت 02:00 UTC، retry و `catchup=False`.
5. اطمینان از نمایش DAG بدون import error.
6. اجرای دستی و بررسی logها.
7. ثبت تاریخ و تعداد ردیف‌ها بدون نمایش secretها.
8. اطمینان از اینکه اجرای تکراری کلیدهای دیتابیس را تکراری نمی‌کند.

Level 3 زمانی کامل است که Airflow اجرا شود، DAG نمایش داده شود، اجرای دستی موفق
باشد، خطای API دوباره تلاش شود، logها مفید و امن باشند و اجرای مکرر duplicate
ایجاد نکند.
